# FrostBox 0.3.0-dev.2 — пользовательский launcher

Эта сборка запускает консольные **Windows x64** приложения на телефоне через Wine + Box64.
Окна Windows и игры с графикой ещё не отображаются. EXE выполняется под UID FrostBox:
приватные каталоги и Wine prefix не являются песочницей для вредоносных программ.

1. Установите APK с включённым Wine/Box64 из поставки. Запустите FrostBox.
2. Library → **Add Game** → **Select EXE**. Системный файловый диалог предоставляет доступ
   только к выбранному файлу. Программа копируется как `games/<UUID>/game.exe`; оригинал не меняется.
   Импорт проверяет PE, вычисляет SHA-256 и сохраняет профиль. Автоматического запуска нет.
3. Если нужны DLL/ресурсы: Details → **Import / replace game folder** → подтвердите выбор папки
   в системном диалоге. Выбирайте каталог конкретной программы, а не корень накопителя.
   Копируются относительные пути в `content/`. Если папка содержит единственный EXE с тем же SHA,
   launcher выбирает его и его родительский каталог как working directory.
   Для других EXE откройте **Game Settings → Select imported EXE**.
4. Game Settings: измените имя, относительные пути, аргументы **массивом JSON** и окружение.
   Пример аргументов: `["--name", "a b"]`. Каждая строка передаётся буквально, без shell.
   Для окружения разрешены WINEDEBUG, WINEDLLOVERRIDES, BOX64_LOG, BOX64_NOBANNER, BOX64_DYNAREC.
5. **Play** выполняет настоящий запуск в отдельном `:runtime`. Появляются Preparing / Starting /
   Running, затем Finished либо Failed. Ненулевой exit code может быть результатом самой программы;
   смотрите Runtime Logs. Отсутствующая DLL должна быть видна в stderr, пока WINEDEBUG её не скрывает.
6. **Stop** отменяет активный процесс; Wine server закрывается адресно. Дождитесь конечного состояния. Пользовательский запуск не имеет автоматического таймаута;
   инициализация prefix ограничена 90 секундами, управление server — 15 секундами.
   В **Runtime Logs** доступны stdout/stderr, PID, код, сигнал, длительность, prefix validation и экспорт JSON.
7. После закрытия/перезапуска FrostBox библиотека и конфигурация сохраняются. После гибели runtime
   показывается Failed; **Recover runtime** сверяет журнал/PID и закрывает оставшиеся процессы.
   Следующий Play восстанавливает runtime, но никогда не перезапускает EXE сам.

Первый prefix требует примерно **655 MiB** дополнительно к runtime и файлам приложения.
Новые записи по умолчанию используют уже выбранный prefix первой существующей записи;
если библиотека пуста, первый Play создаёт собственный prefix. В Game Settings можно явно
выбрать **Own prefix (~655 MiB)** или существующий общий prefix. Общие prefix разделяют реестр,
диск C: и установленное ПО. Запуски сериализованы; один runtime-процесс обслуживает одну операцию.

Импорт потоковый, буфер 64 KiB: EXE до 512 MiB, папка до 16 GiB, 10000 элементов, глубина 32.
Оставляется резерв 64 MiB; обновление папки требует места для новой и предыдущей копий.
Cancel import проверяется между блоками чтения; заблокированный внешний provider может задержать отмену.
Небезопасные имена, Windows reserved names, traversal и конфликты регистра/NFC отклоняются.
При неудаче прежняя папка сохраняется; повторная публикация восстанавливается по журналу.

**Remove library entry** удаляет запись после подтверждения. Приватные файлы и prefix сохраняются,
чтобы не повредить другие записи с общим prefix. Управление удалением этих данных и восстановление
удалённой записи в UI пока отсутствуют. Удаляйте только то, что понимаете; приложение не чистит
пользовательские данные автоматически.

Логи ограничены: stdout/stderr нативного процесса по 32 KiB; UI показывает последние 8 KiB каждого.
Последний результат сохраняется отдельно; runtime NDJSON ротируется примерно на 2 MiB с одной
предыдущей копией. Экспорт относится к текущей операции, а не ко всей истории запусков.
Графические параметры/FPS/XInput скрыты из редактора до реальной интеграции соответствующего пути.

Debug-сборка содержит отдельный read-only provider **FrostBox QA** с исходными тестовыми программами.
Он предназначен для инструментальных проверок; release-сборка не включает этот provider.

В stdout/stderr пока сохраняется байтовое представление старого ProcessManager. ASCII проверен;
автоматический выбор кодовой страницы консоли/UTF-8 не реализован. Не-ASCII вывод может выглядеть
неправильно, даже если Unicode-имя файла импортируется корректно.
